# Database

PostgreSQL schema + Row Level Security for the UAE delivery platform, designed for Supabase.

## Deploying to Supabase

Apply the files in `migrations/` **in order** — either paste each into the Supabase SQL Editor, or use the Supabase CLI:

```bash
supabase link --project-ref <your-project-ref>
supabase db push
```

Then run `seed/0001_default_pricing_rule.sql` once, to create the initial same-day 5km / AED 12 / AED 1-per-km pricing rule the booking flow depends on, with the 90 km individual distance limit (migration 0027 only sets the limit on rules that already exist). Migration 0022 adds the next-day rule (5 km / AED 8 / AED 0.75 per km) and starting merchant flat rates.

You do **not** need to add any `GRANT` statements yourselves — Supabase's managed Postgres already grants `anon`/`authenticated` baseline table and sequence access by default; RLS (enabled on every table here) is the actual restriction layer. The two `GRANT EXECUTE` statements at the end of `0011_public_tracking.sql` are the one exception, needed so the anonymous `/tracking` page can call those two functions.

## Design decisions worth knowing

- **Roles are a Postgres enum** (`customer`/`driver`/`operator`/`manager`), not a separate `roles` table — there's no facility/tenant layer in this build (confirmed decision, see project notes), so a fixed enum is simpler than a lookup table with nothing to look up.
- **`profiles` is the single identity table.** Role-specific fields split into `driver_profiles` (vehicle, license, availability) and `staff_profiles` (employee ID, for both operator and manager) rather than one wide nullable table.
- **Pickup/dropoff live as columns on `shipments`**, not a separate `locations` table — they're 1:1 with a shipment and never reused, so normalizing them out would add a join for no benefit. `driver_locations` (a real time series, reused across pings) *is* its own table.
- **Self-registration can never choose its own role.** The `handle_new_user` trigger always inserts `role='customer'`, regardless of what's in signup metadata. Staff accounts are created by a Manager-only server action using the service-role client, which promotes the role *after* the trigger has already run — see the comment in `0002_profiles.sql`.
- **Price is checked twice.** The booking server action (Phase 5+) computes `distance_km` and `price` itself and never reads them from client input — that's the primary control. `shipments_insert`'s RLS policy also independently re-validates that `price` is mathematically consistent with `distance_km` and the referenced `pricing_rules` row, as a backstop against a request that bypasses the server action and hits the Supabase REST API directly.
- **Status transitions are data, not code.** `shipment_status_transitions` lists every legal `(from, to)` pair; a trigger rejects anything not listed. See that table for the full state machine.
- **`audit_logs`, `payments`, and `notifications` have no INSERT policy for `authenticated` at all.** They're written only by trusted server code using the service-role client, after that code has already checked the actor's role — there is no RLS policy to route around because there's no client-reachable write path in the first place.
- **Public tracking is a function, not a table grant.** `get_shipment_tracking(tracking_number)` / `get_shipment_tracking_history(...)` are `SECURITY DEFINER` functions that return a curated, PII-free subset of a shipment's data (status, ETA, live driver position while in transit) — callable by anonymous visitors on `/tracking`. The `shipments` table itself is never readable by `anon`.
- **Package photos are folder-scoped by uploader, not by shipment.** The photo is uploaded during booking, before the shipment row exists, so the upload-time RLS policy checks the path prefix against `auth.uid()`. Read access is broader once the shipment exists: the uploader, any staff member, or the shipment's assigned driver (via a join back to `shipments.package_image_url`) can view it.
- **Proof-of-delivery evidence is folder-scoped by shipment, not by uploader.** Unlike package photos, this is uploaded by the driver after the shipment already exists, so `proof-of-delivery` bucket policies (migration 0013) key off `shipments.id` in the path and join back to check `driver_id`/`customer_id`/staff — the uploader, the customer, and staff can all view it; nobody else can.
- **A driver can't null out their own `driver_id` through the ordinary RLS update policy** — declining an assignment needs the new row's `driver_id` to be `null`, which fails `shipments_update`'s `WITH CHECK` for a non-staff caller by design. `decline_shipment_assignment()` (migration 0013) is a narrow `SECURITY DEFINER` function that checks the caller is actually the assigned driver and the shipment is still `'assigned'`, then makes that one specific state change — a scalpel, not a policy loosening.
- **Row-level access isn't column-level access.** RLS decides *which rows* a session can update, not *which columns or statuses*. `enforce_shipment_update_permissions` (migration 0015) closes that gap: customers may only cancel their own shipment; drivers may only move status through the driver workflow and set a failure reason; staff are unrestricted. It only applies to direct client sessions (`current_user = 'authenticated'`) — `SECURITY DEFINER` functions and the service-role client do their own checks. Before 0015, a customer could assign a driver to their own shipment and advance it through legal driver-only transitions; this was found by probing during Phase 9, not by review.
- **Delivery secrets live where drivers can't read them.** The QR token and delivery OTP are in `shipment_secrets` (RLS on, no policies at all). `issue_delivery_otp()` generates the code and notifies the customer inside the database; `complete_delivery()` is the only path to `'delivered'` — it verifies OTP/QR against the secrets table, checks any photo/signature path really exists in that shipment's storage folder, requires at least one proof, and records `proof_of_delivery` atomically. Wrong OTPs return `'invalid_otp'` (rather than raising, which would roll back the counter) and the code is invalidated after 5 attempts. Drivers can no longer insert `proof_of_delivery` directly.
- **Delivery OTP has no SMS provider behind it.** The generated code (stored in `shipment_secrets` since migration 0015) is delivered via the customer's in-app notification feed rather than a text message, since no SMS integration is configured in this build. Swap in a real provider by changing how `issue_delivery_otp()` delivers the code — storage and verification don't need to change.

- **Only the active pricing rule prices client bookings** (migration 0016). The price check previously accepted any rule id, so after a Manager changed pricing a customer calling the API directly could keep booking at a retired, cheaper rate.
- **Business tagging requires membership** (0016). A customer can only attach `business_account_id` for a business they belong to; otherwise they could inject shipments into another company's history and billing.
- **The manager role is locked** (0016). No application session — not even a manager's — can grant or revoke `manager`; that's done from the Supabase dashboard (see the root README). All three 0016 gaps were found by probing before the Manager dashboard was built.
- **Notifications are fired from one place: table triggers, not application code.** `shipments` changes reach the database through four different code paths (customer cancel, driver status advance, operator assign/reassign, and the `complete_delivery`/`decline_shipment_assignment` functions). A single `AFTER INSERT`/`AFTER UPDATE` trigger pair (migration 0017) is the one place that sees every path, so it's the reliable place to fire customer/driver/operator notifications from — scattering inserts across each call site would eventually miss one. The one app-level notification insert that existed before this (`lib/dispatch/actions.ts`) was removed once the trigger covered it, to avoid duplicates.
- **QR label printing and pickup verification go through purpose-built functions, not a table read.** `shipment_secrets` (0015) still has zero policies. `get_shipment_qr_token()` returns the token to the customer, the assigned driver, or staff, for printing a label. `verify_shipment_qr()` is read-only — it tells a driver's scan whether it matches, without revealing the correct value and without changing any state, so an optional "verify at pickup" scan can't be confused with the mandatory proof-of-delivery check `complete_delivery()` already does.
- **Functions are not callable by default** (migration 0018). Postgres grants `EXECUTE` on new functions to everyone, which let any signed-in user call the internal `notify_operators()` helper and message every staff member (found in the Phase 12 audit). It's now revoked, and default privileges in the schema are changed so future functions start with no grants. Every client-callable function is granted deliberately. Also in 0018: random tracking numbers, the `rate_limits` table and `check_rate_limit()` (service-role only), bcrypt-hashed delivery OTPs, and server-side upload size/type limits on both storage buckets.
- **Duplicate submissions can't create duplicate shipments** (migration 0019). The booking wizard sends one request id per booking attempt; a unique index on `(customer_id, client_request_id)` guarantees one shipment per id even when two requests race, and the app returns the original shipment instead of an error.
- **Bulk shipment lists are batches** (migration 0020). A customer's bulk list is a `shipment_batches` row, and each shipment created from it carries `batch_id`. A trigger lets a shipment join only an open batch that belongs to the same customer, so nobody can slip shipments into someone else's list. Customers may only open a batch in its initial state; finalizing it (counts, failed rows, status) is done with the service-role client. Batch shipments skip the per-shipment "booked" and "ready for dispatch" notifications, and a single batch-level notification goes to the customer and to every operator and manager instead. The manager's business-account CSV upload goes through the same batch pipeline.
- **Performance pass** (migration 0021). Hot read policies wrap `auth.uid()` / `is_staff()` as `(select ...)` so Postgres evaluates them once per query instead of once per row; conditions are unchanged. Adds indexes for the app's newest-first lists, the dispatch queue and business membership lookups. Adds `security_invoker` aggregate views (`customer_shipment_stats`, `driver_shipment_stats`, `driver_cod_stats`, `batch_shipment_stats`, `business_shipment_stats`, `cod_status_totals`): they run under the caller's RLS, so they only aggregate rows the caller could already read. List pages use them instead of downloading every shipment and counting in JavaScript, which also silently broke past PostgREST's 1,000-row response cap.
- **Merchants, delivery types, weight/COD pricing, distance limit and short tracking codes** (migration 0022).
  - `profiles.account_type` is `individual` or `merchant`. No client session can change it — only `review_merchant_application()`, which checks the caller is a manager. `merchant_applications` holds one application per customer (company, contact and shipping details, optional trade licence in the private `merchant-documents` bucket). Applicants can edit only after a manager requests changes or rejects; approval creates/re-activates a `business_accounts` row and adds the merchant as its member, so the existing business pages and CSV upload work for merchants. Company details are readable by the applicant and managers only. A trigger sends the in-app notifications; the app sends the email.
  - `pricing_rules` now has one active rule per (`delivery_type`, `account_type`), plus `included_weight_kg`, `additional_price_per_kg`, `cod_fee` and `max_distance_km`. Merchant flat rates are rules with `additional_price_per_km = 0`. Merchant rules are readable by merchants and staff only.
  - `shipment_price_is_valid()` re-derives every component (`base_charge`, `distance_charge`, `weight_charge`, `cod_charge`) against the active rule for the shipment's delivery type and the customer's real account type, refuses trips over the rule's `max_distance_km`, and requires a weight for merchants. `enforce_shipment_distance_limit` refuses over-limit trips for **every** caller, staff included.
  - Shipments store `recipient_payment_type` (`prepaid`/`postpaid`) and `cod_amount` — what the driver collects for the goods, never the delivery fee — separately from `product_value`. A CHECK makes prepaid ⇔ `cod_amount = 0`.
  - `cod_transactions` rows are now created by a trigger when a driver is assigned, split into `product_amount` and `delivery_fee_amount`. Before this, the app inserted them without the required `driver_id`, so the insert always failed silently and no COD record was ever created.
  - `tracking_number` is an 8-character code from a 31-symbol alphabet (no 0/O/1/I/L), always generated by a trigger and immutable. Existing numbers were moved to `legacy_tracking_number`; the public lookup accepts either, case-insensitively.
- **Merchant bulk shipments** (migration 0026). A merchant's CSV upload is a `shipment_batches` row in the new `draft` state, with one `shipment_batch_rows` row per CSV line. The server resolves, coverage-checks, routes and prices each row (`quote`), and the merchant reviews and fixes rows before booking. `shipment_batch_rows` has a SELECT policy only, so just the service-role client writes it, after the server has matched the batch to the signed-in merchant. A client can never plant a distance or price. Booking moves the batch `draft → processing` with a conditional update (a double click finds it taken). It then inserts every bookable shipment in **one** statement with the merchant's own session: Postgres makes that all-or-nothing, and `shipments_insert` still re-checks each price. Each shipment's `client_request_id` is its row id, so the 0019 unique index allows one shipment per row. A failed booking returns the batch to `draft`, and the batch notification ignores that transition. `cancelled` is a discarded draft. Neither state can hold shipments (the 0020 ownership trigger requires `processing`), and staff lists leave both out. Also adds the nullable `shipments.delivery_date`. Rows are validated through a queue: `claim_batch_rows()` (service role only) hands each pending row to one worker with `FOR UPDATE SKIP LOCKED`, and a claim older than two minutes is taken again. The worker is either the merchant's open tab or the background route `/api/internal/bulk-worker`. `maps_cache` (RLS on, no policies) shares resolved addresses and routes across server instances.
- **Distance limits** (migration 0027). `pricing_rules.max_distance_km` is now nullable: `null` means no limit. Merchant rules are set to `null` (merchants can send any distance) and individual rules to 90 km. `enforce_shipment_distance_limit` takes the limit for a booking without a pricing rule from the customer's own account type rather than the largest active limit.
- **Driver delivery outcomes** (migration 0028).
  - `complete_delivery()` no longer asks for a recipient name (the parameter stays, optional, so older calls still work). A delivery photo is now required; signature, OTP and QR remain optional extra proof. On a postpaid shipment the driver must confirm the COD amount was collected: the confirmation is stored as `proof_of_delivery.cod_collected` and the shipment's `expected` COD record becomes `collected` in the same transaction.
  - The recipient pays `cod_amount` only. The app computes this in one place (`lib/shipment/collection.ts`); the delivery fee, when the sender pays it in cash, is the sender's and is never added to the recipient's amount. `cod_transactions` keeps the two apart as `product_amount` and `delivery_fee_amount`.
  - Drivers can cancel before pickup (`driver_cancel_shipment`, from `driver_accepted`/`arrived_pickup`) and return a picked-up parcel to the sender (`driver_return_shipment`, from `picked_up`/`in_transit`/`arrived_destination`). Both are narrow `SECURITY DEFINER` functions that check the caller is the assigned driver and require a reason; `enforce_shipment_update_permissions` is unchanged, so a plain update to `cancelled`/`returned` is still refused. The reasons use the existing `cancelled_reason` and `delivery_failed_reason` columns. New transitions: `arrived_pickup → cancelled` and `picked_up`/`in_transit`/`arrived_destination → returned`.
  - A driver cancellation or return notifies the customer and operations; a cancellation by the driver no longer tells the driver it was "cancelled by the customer".

- **Operator shipment categories and customer search** (migration 0030).
  - `staff_shipment_feed` (`security_invoker`) lists every shipment that is *not* in a batch plus every staff-visible batch as **one** entry, newest first, with the booking customer's `account_type`. The staff Shipments page pages through it in the database and filters it: Individual / Merchant by `account_type`, Bulk by `kind = 'batch'`. Bulk is the existing `shipment_batches` relationship — never inferred from a quantity — so a 25-shipment booking is one entry that opens to its 25 shipments. The page's shipments and batches are then loaded by id (three queries per page).
  - `search_customers(query, limit, offset)` matches a customer's name or the company name of a business account they belong to — partial, case-insensitive, with `%`, `_` and `\` in the query escaped so they match literally — and returns one page plus the total. `SECURITY INVOKER` with an explicit staff check: a customer calling it gets nothing. Company names come from `business_accounts` (staff-readable), not `merchant_applications` (managers only). Trigram GIN indexes (`pg_trgm`, in whichever schema it is installed) serve the substring matches.
- **Invoices** (migration 0031).
  - `invoices` + `invoice_line_items`. Types: `individual_shipment`, `merchant_shipment` (a merchant's shipment outside any batch) and `bulk_shipment` (one invoice for a merchant's whole batch). A merchant's batched shipment is billed only on the batch's invoice, so no shipment is ever invoiced twice; at most one live (`issued`) invoice exists per shipment and per batch (partial unique indexes).
  - Written only by `issue_shipment_invoice()` / `issue_batch_invoice()` (`SECURITY DEFINER`, callable by `authenticated`). They check the caller booked the shipment or belongs to its business account (anyone else gets "not found"), refuse cancelled shipments and unbooked batches, and copy every amount from the stored, already price-checked shipment columns — `price` is the amount billed; weight and COD charges are the additional charges, the rest is the delivery service. Nothing comes from the request. A bulk invoice's lines are one `INSERT … SELECT` with the batch's shipments held `FOR SHARE`, and the header must equal the sum of its lines. Calling either again returns the same invoice (an advisory lock makes concurrent clicks safe). Each issue writes an `invoice.issued` audit log row.
  - **Immutable snapshot.** Billed-to details, lines and totals are copied at issue time; triggers refuse any update or delete — the service role included — except `issued → void` (with `voided_at`/`void_reason`), the hook for an explicit, audited regeneration: void the old invoice, issue a new one, both stay on record.
  - RLS: `invoices_select` matches `shipments_select` minus drivers — the customer, members of the billed business account, and staff. Lines follow their invoice. No client write policies.
  - Helpers (`next_invoice_number`, `invoice_caller_may_issue`, `invoice_billed_to`) have EXECUTE revoked explicitly. Note: 0018's `alter default privileges in schema public revoke execute on functions` cannot remove Postgres's *global* EXECUTE-to-PUBLIC default, so every new function needs an explicit `revoke … from public` (as 0024 does for `anonymize_profile`).

- **Driver shipment search** (migration 0035). `search_driver_shipments(query, statuses, from, to)` is the driver's counterpart of `search_customer_shipments()` (0032): same parameters, matching rules and paging, so the driver's My Deliveries page reuses the customer list's filters. Its scope is `driver_id = auth.uid()` inside the query — there is no driver id parameter to swap — and it is `SECURITY INVOKER`, so `shipments_select` RLS still applies. One search box matches sender/recipient name, tracking number (current or legacy), pickup/drop-off address and building, or phone; status and UAE booking date combine with it by AND. Anyone not assigned a shipment (customer, staff, anonymous) gets nothing; `anon` can't call it.
- **Merchant status cards and fuller search** (migration 0036). `customer_shipment_status_counts()` returns the caller's own shipments per status in one grouped query (`customer_id = auth.uid()`, `SECURITY INVOKER`, no id parameter); the dashboard's cards, including the merchant's In transit / Delivered / Returned / Cancelled, read from it. Bulk shipments count shipment by shipment. `search_customer_shipments()` now also matches the shipment ID (current or legacy) and the pickup/drop-off address and building, like the driver search; its signature and scope are unchanged.
- **Every driver outcome needs a photo and a reason** (migration 0037). Delivered, returned and cancelled all require both. `driver_cancel_shipment` / `driver_return_shipment` now take a `p_photo_path`, checked like the delivery photo (inside the shipment's folder in `proof-of-delivery`, and really uploaded); the old two-argument versions are dropped so the photo can't be skipped. Each return or cancellation is recorded in `shipment_outcome_proofs` (append-only, no write policies; readable by the shipment's driver, its customer and staff — the same audience as `proof_of_delivery`). `complete_delivery()` also requires the delivery note.
- **Staff shipment search** (migration 0038). `search_staff_shipments(query, statuses, from, to, account_type, bulk_only, batch_id)` backs the operator and manager Shipments list's search and filters: the same matching rules and paging as the customer (0032/0036) and driver (0035) searches, over every shipment, plus the booking customer's name or email, the business account's company name and the driver's name. It returns nothing unless the caller is staff (`is_staff()`), whatever RLS would allow, and is `SECURITY INVOKER`. Because staff search the whole table, the text match runs against `shipment_search_document()` (the searched fields, lower-cased, one per line) through a trigram index, `shipments_search_trgm_idx`.
- **Bookings for customers without an account** (migration 0040). Operators and managers can book for someone who contacted ParcelLink by WhatsApp, phone or in person and has no account. A profile is one `auth.users` row, so such a customer can't have one without a fake sign-in, and a shared "walk-in" profile would merge unrelated people's histories. Instead `shipments.customer_id` is nullable and the shipment carries `guest_customer_name` / `guest_customer_phone`, plus `booked_by` (the staff member, from the session). A CHECK makes every shipment have either a customer or complete guest details (never both). Guest details are never matched or merged with registered customers. `shipments_insert` already allowed only staff to insert a shipment that isn't their own, so only staff can create one; the policy now also requires `booked_by` to be the caller. Guests are priced as individuals by the same server-side quote; the distance limit takes the individual limit when there is no customer. A guest booking can't join a batch and has its own duplicate-submission index (`booked_by`, `client_request_id`). Customer notifications for a shipment with no customer are dropped by one `BEFORE INSERT` trigger on `notifications` (rather than failing the booking or a status change); `issue_delivery_otp()` refuses with a clear message, since the code goes to an in-app feed a guest doesn't have (the delivery photo is always required anyway). `staff_shipment_feed` and `search_staff_shipments()` list guest bookings under Individual and search the guest's name and phone. Public tracking already returns no personal details. Invoices remain customer-issued, so a guest booking has none.
- **Status corrections** (migration 0041). `correct_shipment_status(shipment, expected_status, new_status, reason)` lets operators and managers fix a status a driver set by mistake without loosening `shipment_status_transitions`: the transition trigger only skips its check for an UPDATE running inside that SECURITY DEFINER function (a transaction-local flag *and* a non-client `current_user`), so a direct client update can never use it. Allowed: from a driver-workflow status (assigned … arrived_destination, delivery_failed) to another of assigned … arrived_destination, with a driver assigned; re-opening a cancelled/returned shipment is managers only; `delivered` is never a source or target (proof of delivery and cash collection hang off it). The caller passes the status they saw — a stale view is refused. A reason (5–500 characters) is required. `shipment_status_history` stays append-only: the correction is a new row with `event_type = 'correction'`, `previous_status` and the reason in `note`; every row now records `previous_status`. Proof of delivery, outcome photos and reasons are untouched. Status notifications are skipped for a correction (a customer isn't told "picked up" after a parcel was wrongly shown "in transit"); the driver gets one `shipment.status_corrected` notice; an `audit_logs` row is written in the same transaction. `get_shipment_tracking_history()` now also returns `event_type` (still no notes or people) so the tracking page leaves out steps a correction undid.
- **Driver cash reconciliation** (migration 0042). `cod_transactions.collected_amount` / `collected_by` are written by a trigger the moment a row becomes `collected` — from the row's own amount and the session, never the request — and can't be changed afterwards by anyone. Rows collected before this migration keep `collected_amount` null and are shown as *unverified*, outside the balance, rather than given invented amounts. `driver_cash_remittances` records each cash handover (AED, method, reference, day received) as `pending → confirmed | rejected`; it has a staff-only SELECT policy and no write policies, and a trigger refuses deletes and any change but that one decision, for every role including the service role. `record_driver_remittance()` (operators and managers; a manager's is confirmed at once) and `decide_driver_remittance()` (managers; rejecting needs a reason) take a per-driver advisory lock, refuse more than the driver owes (less other pending remittances), return the original row for a repeated `client_request_id`, and write `audit_logs`. Confirming settles the driver's oldest verified `collected` rows (→ `reconciled`, with `remittance_id`) as far as confirmed cash covers them in full; a verified row can no longer be reconciled one by one without a remittance, so the same cash can't be settled twice. Balances: *outstanding* = verified collected − confirmed remitted (always as of now); *expected* = amounts on `expected` rows (still to collect, not cash held); *pending* and *unverified* are shown separately. `driver_cash_summary()` / `driver_cash_totals()` compute these per driver in the database (SECURITY INVOKER, staff only); a date range filters period activity only, never the balance.
- **Operator booking emails use an outbox** (migration 0043). Triggers on `shipments` (insert) and `shipment_batches` (leaving `processing`) queue one `operator_booking_emails` row for each booking a customer made themselves. The row is written in the booking's own transaction, so a rolled-back booking queues nothing. A unique `shipment_id` / `batch_id` means one row per booking at most. "Made themselves" means `auth.uid() = customer_id` with no `booked_by` for a single shipment, and `created_by = customer_id` for a batch, so staff-entered bookings are skipped. Batch shipments are skipped one by one, and the batch is queued once. The table has RLS on, no policies and no grants. It has no recipient column, because the recipient is server configuration. `claim_operator_booking_emails()` (service role only) gives each due row to one worker, using `SKIP LOCKED` and a lease, and counts the attempt before anything is sent.
- **Financial reporting** (migration 0044). One calculation engine, `financial_shipment_lines(from, to, business_account_id)`, returns one row per shipment *completed* in a period (Asia/Dubai days): delivered (the `delivered` history row — terminal, never corrected) or returned (the latest `returned` row). Booking date is never used. Every amount is aggregated per shipment before joining, so no join can multiply a row: `service_charge` = `price` (delivered only); `return_charge` = 50% of `price − cod_charge` (returned merchant shipments only); `cod_collected` = `product_amount` of **verified** collections (0042 `collected_amount` set); `cash_handling_fee` = 1.5% of that, per shipment; `payments_received` = verified cash delivery fee + `payments` marked `paid`; `cod_remitted` = verified goods money already marked `remitted`. Pre-0042 (unverified) and missing collections are reported separately and excluded from every total. Manager only (returns nothing to anyone else). `merchant_statements` / `merchant_statement_lines` snapshot it (the invoice pattern of 0031): `generate_merchant_statement()` writes a manager-only **draft**; `publish_merchant_statement()` numbers it (`STM-YYYY-NNNNNN`, no gaps), notifies the merchant's members and makes it visible to them through RLS; a correction is a new draft with `supersedes_id` and a reason that, when published, marks the original `superseded` (kept, still visible). Triggers refuse every other change — and deletion of anything but a draft — for every role including the service role. A published statement can't overlap another live one for the same merchant, and the same shipment completion can't be on two live statements. `net_amount = total_cod − cod_already_remitted − service − returns − cash_handling + payments_received` is a table constraint. `expenses` / `expense_categories` are manager-only (RLS), never deleted (void with a reason), audited by trigger; each category has a `profit_group` (fuel / subscription / salary / rent / other) so `business_performance_summary()` can compute R, the four cumulative profit steps, net operating profit and the break-even gap in numeric.
- **Rates, statement emails and settlements** (migration 0045). The return-charge and cash-handling rates live in `financial_rates`, an append-only history keyed by `effective_from`; `financial_policy(day)` returns the rates in force on a day, and `financial_shipment_lines()` charges every shipment at the rate in force on the day it was completed, so a new rate never changes an issued statement or an earlier period of the performance report. `set_financial_rates()` (managers) only accepts today or later and replaces a rate still scheduled for a future day; a trigger refuses any change to a rate already in force, for every role. Each statement line stores the rates it was charged at, and the header flags `rates_vary`. Publishing can queue a `merchant_statement_emails` row (an outbox like 0043, service role only). `merchant_statement_settlements` records money actually paid out to or received from the merchant against the current published statement: `record_statement_settlement()` derives the direction from the balance, refuses more than is outstanding, dedupes retries by `client_request_id`, notifies the merchant and audits; settlements are never edited or deleted, only voided with a reason. `merchant_statement_balance()` counts settlements on the statement and every statement it corrected, so a correction never asks for money already paid. Once a shipment is on a published statement, the per-shipment COD `remitted` step is refused (`cod_transactions_prevent_statement_remit`), so its COD can't be paid out twice.
- **Staff price changes and cancellation** (migration 0046). `staff_adjust_shipment_price(shipment, expected_status, expected_price, new_service_charge, reason, request_id)` and `staff_cancel_shipment(shipment, expected_status, reason, request_id)` are the only way operators and managers change a booked shipment's price or cancel it; a plain client update of the money columns (`price`, the charge components, `price_adjustment`, `cod_amount`, `recipient_payment_type`, `payment_method`, `currency`) or to `cancelled` is now refused for staff (customers keep their own cancel, drivers theirs). Both check the role and an active profile from the session, lock the row, refuse a status (and price) the caller didn't see, require a reason (5–500 characters), return the first result for a repeated `request_id` without a second change, notification or audit row, and write one `audit_logs` row (`shipment.price_adjusted` / `shipment.cancelled_by_staff`) in the same transaction. **Price:** the operator sets the delivery *service* charge (AED 0–10,000, two decimals); weight and COD-handling charges stay as calculated, the difference goes to the new `price_adjustment` column (so `price` = calculated charges + adjustment) and `cod_amount` is never touched. Refused once delivered/cancelled/returned, once the fee is paid (`payment_status` paid/refunded or a paid `payments` row) or collected in cash (a non-`expected` `cod_transactions` row carrying the fee), or when the shipment is on a merchant statement — there is no refund/extra-charge workflow to absorb it. The driver's still-`expected` cash record follows the new fee; a live invoice covering the shipment (its own or its bulk invoice) is voided with the reason so the customer issues a corrected one; the customer is notified. **Cancel:** allowed from `pending_payment`, `confirmed`, `assigned`, `driver_accepted`, `arrived_pickup` (no new transitions); a picked-up parcel is returned by the driver, a failed delivery is marked returned. `driver_id` is kept for history; active driver lists and counts drop it by status; the 0022 trigger drops only the `expected` cash record, collected cash stays in the driver's balance; payments, invoices and statements are untouched — a paid fee is flagged `refundRequired`, never marked refunded. The customer and driver are told operations cancelled it. `shipment_staff_actions(shipment)` (staff only) returns what is allowed and why, plus the money already attached, so the dialogs match the rules.
- **Mobile app push notifications** (migration 0047). Additive only: no existing table, policy or trigger changes. `mobile_push_devices` holds each ParcelLink app install's Expo push token (one row per token, owned by whoever signed in on it last); people read only their own rows and nobody writes directly — `register_push_device(token, platform)` (active drivers, operators and managers only) and `unregister_push_device(token)` (own tokens only) run as the caller. `notification_push_deliveries` is the push outbox (service role only): `claim_push_notifications(limit, lease_seconds, max_attempts, max_age_minutes)` hands each recent notification of an active app user with an enabled device to exactly one worker (leased, attempt counted first, never past the cap, never after it was sent), reading notifications per device owner through the existing `(profile_id, created_at)` index. The website's `/api/internal/push-worker` sends them through Expo and disables tokens Expo reports gone. The notifications themselves are never changed, so a push problem can't affect the action that created them. See `mobile/docs/CONFIGURATION.md` for the webhook that triggers the worker.
- **Cash only, and weekly remittances driver → operator → manager** (migration 0048). *Card off:* `payment_settings` (one row, `card_payments_enabled` default false, no client write path) and the `shipments_enforce_cash_only` trigger refuse any client session — staff included — creating a card shipment or switching one to card while it's off; trusted code checks the app's `CARD_PAYMENTS_ENABLED` itself. `switch_shipment_to_cash()` moves a card shipment still `pending_payment` (customer or staff; no card payment on it) to cash and `confirmed` without marking anything paid; its notification says "paying in cash", never "payment successful". *Driver → operator:* `driver_cash_remittances` (0042) gains `source` ('driver' submissions vs 'staff'-recorded), a `remittance_number` (`DRM-YYYY-NNNNNN`, existing rows numbered too), a COD/fee split (`cod_amount` + `fee_amount` = `amount`; null on staff-recorded rows), `period_start` (Monday, Asia/Dubai), the custodian (`received_by`, `received_by_role`), status `disputed`, and `discrepancy_of`. `submit_driver_remittance()` (drivers; per category ≤ verified collections − confirmed − pending, under the 0042 per-driver lock; a repeated request id returns the first row) creates a pending row — reserved, never deducted. `confirm_driver_remittance()` (operators or managers) confirms exactly what was submitted, or — when less was counted, with a reason — closes the submission `disputed` with both amounts and records the counted cash as its own confirmed row linked by `discrepancy_of`; more than submitted is refused. `dispute_driver_remittance()` counts nothing. Confirmation settles collections as 0042 did. Drivers can now read their own remittances. *Operator → manager:* `operator_cash_remittances` (same shape, `OPR-YYYY-NNNNNN`, RLS: the operator's own or a manager's; no write path; frozen once decided). An operator's balance is only the driver cash they confirmed (`received_by_role = 'operator'`) minus what a manager confirmed from them, so the same cash is counted once at each level; driver cash a manager confirms directly never passes through an operator. `submit_ / confirm_ / dispute_operator_remittance()` mirror the driver functions (operators submit, managers decide). *Read:* `driver_cash_overview()`, `driver_cash_weeks()`, `driver_remittance_history()`, `driver_remittance_queue()`, `operator_cash_overview()`, `operator_cash_weeks()`, `operator_remittance_history()`, `operator_cash_balances()`, `manager_cash_totals()` — each checks the caller (self, staff or manager as fits). Weekly summaries open with what was still held when the week began (carried forward, never reset). Submissions, confirmations, discrepancies and disputes notify the next person in-app (one notice per decision; repeats notify no one) and write `audit_logs`.
- **Driver details for staff** (migration 0049). Read-only. `staff_driver_shipments_matching(driver, query, from, to)` is the one definition of "this driver's shipments" (assigned = current `shipments.driver_id` — there is no assignment history; booking date in Asia/Dubai days; partial, case-insensitive search over id prefix, tracking numbers, names, addresses and — for terms without letters — both phones by `phone_search_key()`), read by both `staff_driver_shipment_counts()` (per status) and `staff_driver_shipments()` (paged list with each shipment's own price and COD amount, plus what this driver collected on it from a per-shipment `cod_transactions` aggregate, so no join can repeat a shipment) — a filter's count is always its rows. `staff_driver_overview(driver, from, to)` returns the driver, charges on shipments booked in the period, **verified** COD and fee collected in the period by `collected_at` (expected cash is never collected), cash still to collect, and the balance now from 0048's `driver_cash_breakdown()`. All staff only (explicit `is_staff()`). Every operator sees every driver — by design, as in dispatch and 0048's cash confirmations; there is no per-operator driver scope. `driver_cod_stats` (0021) keeps `collected_total` and gains `cod_collected` / `fee_collected` (verified, split), which the Drivers list and the driver's home page now show instead of the mixed lifetime total.
- **Merchant fee policy** (migration 0050). `merchant_fee_policy(delivery_type, recipient_payment_type, order_count)`: a COD (postpaid) merchant shipment has **no** delivery fee; non-COD Next-Day is AED 20 flat for 2–4 orders booked together and AED 15 flat for 5+; anything else (one order, Same-Day) keeps the merchant pricing rule, tier `unconfirmed`, until a rate is agreed. Order count = the shipments of one booking or bulk upload (`shipment_batches`; none = 1), fixed when the batch leaves `processing`. The database sets every merchant price: `shipments_price_merchant` (BEFORE INSERT, client sessions only — detected by the session's `role` setting, since it runs as its owner) prices the row whatever the request said, refuses a non-merchant rule, a missing weight (non-staff) or — for a single booking, whose size is final — a price that isn't the policy's; `reprice_merchant_batch()` (fired by `shipment_batches_finalize_merchant_fees`) sets the final tier for a batch, audited per changed price, keeping its bulk rows in step. `shipments.fee_billed` marks a fee billed to the merchant account (invoice/statement), never driver cash: `cod_transactions_billed_fee` strips it from every `expected` cash record (from the 0022 sync, 0046's price edit or anything else) and skips the record when no COD is left; collected records are history and untouched; individual customers' cash fees are unchanged. `merchant_fee_tier` / `merchant_order_count` / `fee_billed` can't be set by any client (`shipments_guard_merchant_fee`, and 0006's pricing guard now judges client sessions only). Existing open merchant shipments became `fee_billed`, lost the fee from their expected cash records, and — unless invoiced, on a statement or staff-adjusted — were re-priced at their booking's size, each audited. The 0044/0045 1.5% cash-handling charge (a merchant-statement line, never taken from a driver's remittance) was then removed by 0051.
- **No cash-handling charge** (migration 0051). The 1.5% cash-handling fee of 0044/0045 is gone: merchants are billed only the flat delivery rates of 0050 and the COD collected for them is paid out in full. `financial_shipment_lines()` returns `cash_handling_fee` = 0 and `cash_handling_rate` = 0 on every line, so drafts, new and regenerated statements, the performance report and its export carry none; `financial_policy()` reports a 0 rate; `set_financial_rates()` (now a wrapper of the 0045 function, renamed `set_financial_rates_0045`) refuses any non-zero cash-handling rate. Published statements are never edited: one issued with the charge keeps it, and a correction is issued without it. The migration lists any unpublished draft still carrying the charge, to discard and regenerate.
- **Operator expense reports** (migration 0052). Operators record their own expenses (`expenses.source` = 'operator', set by the database from the session; existing rows are 'manager') with an optional receipt in the private `expense-receipts` bucket (uploader's own folder; readable by them and managers). `expense_reports` (EXR-YYYY-NNNNNN) are weekly (Monday–Sunday), monthly (calendar month) or custom (≤ 93 days), Asia/Dubai dates; an operator's report periods never overlap and each expense belongs to the report covering its date (`expenses.report_id`, set by `expenses_operator_rules`), so every expense is in at most one report. `create_ / submit_ / discard_expense_report()` (operators) and `approve_ / return_expense_report()`, `correct_expense()` (managers) are the only writers: each takes the actor from the session, locks the report, allows only its status's transitions (draft → submitted → approved | returned → submitted), records `expense_report_events` (append-only; the operator reads their own) and the audit log, notifies once, and answers a repeat with the current state. A submitted report's expenses are frozen; an approved one changes only through `correct_expense()`, which keeps the original amount in `expense_corrections`. **Official figures** (`business_performance_summary()`, `expense_category_totals()`, so the page and its export) count manager-recorded expenses and operator expenses in approved reports only (`expense_is_official()`), so no pre-0052 figure moves; `expense_review_summary()` shows what is awaiting review, returned or not submitted — each expense in exactly one bucket. Operators read the categories; only managers change them. Read helpers: `my_expense_totals()`, `expense_report_list()`, `expense_report_history()`, `expense_report_categories()`.
- **Realtime** (migration 0014) publishes `shipments` and `driver_locations` for the live dispatch map. Supabase Realtime applies each subscriber's RLS, so no extra policies are needed — but Realtime itself can't run in the local harness, so the live-update behaviour is only verifiable against a real Supabase project.

## Local verification (`test/`)

Everything in `test/` is a local-only harness — it is **not** deployed to Supabase. It applies all migrations to a scratch Postgres database and runs a battery of RLS attacks (role self-promotion, price tampering, illegal status jumps, cross-role data access, direct writes to service-role-only tables, etc.) to confirm they're actually blocked, not just reviewed by eye.

```bash
# requires a local Postgres with a postgres superuser
sudo apt-get install postgresql && sudo service postgresql start

bash database/test/run.sh          # applies migrations + seed to a scratch DB
sudo -u postgres psql -d uae_delivery_test -f database/test/attacks.sql 2>&1 | python3 database/test/grade.py
```

Two more suites run against the same scratch database:

```bash
sudo -u postgres psql -d uae_delivery_test -f database/test/transitions.sql   # every status transition
sudo -u postgres psql -d uae_delivery_test -f database/test/customer-search.sql  # shipment search, status counts + bulk label tokens
sudo -u postgres psql -d uae_delivery_test -f database/test/merchant-pricing.sql # merchant flat rate AED 15 (0033)
sudo -u postgres psql -d uae_delivery_test -f database/test/merchant-repricing.sql # existing merchant shipments to AED 15 (0034)
sudo -u postgres psql -d uae_delivery_test -f database/test/driver-search.sql   # driver shipment search (0035)
sudo -u postgres psql -d uae_delivery_test -f database/test/staff-search.sql    # operator/manager shipment search (0038)
bash database/test/price-consistency.sh    # needs the e2e database: bash e2e/stack/setup-db.sh
```

`customer-search.sql` checks migrations 0032 and 0036 on its own fresh scratch database (it adds its own users): every name, phone, shipment ID, address, status, UAE-date and combined search, the status-card counts (bulk shipments counted individually) following status changes, the business-wide list matching the Shipments card's count, bulk label QR tokens, operator edits reaching the merchant, and that no other merchant (or anonymous caller) gets any of it. Each check raises `FAIL …` when wrong.

`driver-search.sql` checks migration 0035 on its own fresh scratch database: name, shipment ID (current and legacy), pickup/drop-off address, phone, status, UAE-date and combined searches, operator edits and reassignment reaching the driver's results, and that no other driver, customer, staff member or anonymous caller can find a driver's shipments through it.

`staff-search.sql` checks migration 0038 on its own fresh scratch database: shipment ID (current and legacy), sender/recipient name and phone, pickup/drop-off address, customer, company and driver, status, UAE date, the Individual / Merchant / Bulk tabs and one bulk batch, all combined; operator edits showing up; that drivers, customers and anonymous callers get nothing; and that the text search can use its trigram index.

`guest-bookings.sql`, `status-corrections.sql` and `driver-cash.sql` check migrations 0040, 0041 and 0042 on their own fresh scratch databases: who may book for a customer without an account, the guest details, distance limit and duplicate protection, dispatch, delivery and cash collection on a guest shipment, and that public tracking shows no personal details; every correction rule (roles, reason, stale view, unlisted and delivered targets, the client-side bypass attempt), the history trail, notifications, audit log and kept evidence; and the driver cash example (AED 1,000 collected, 600 remitted, 400 outstanding, 200 still to collect), pending / rejected / confirmed remittances, double submissions, oldest-first settlement, permanent records, date ranges, and who may see or change any of it.

`merchant-fee-backfill.sql` is the exception to the order above: run it on a database migrated only up to 0049 (it applies 0050 itself with `\ir`) to check how 0050 treats shipments booked before it.

`concurrency.mjs` races the remittance, merchant-booking and expense-report functions from many real sessions at once (ten submissions of the same cash, retried request ids, two operators or two managers confirming the same remittance, confirm against dispute, a submission against a confirmation) and checks only one wins and the balances still add up. The `.sql` suites run in one session and can't show this. It needs the `pg` client, which the app doesn't use: after `run.sh`, `npm install --no-save pg` and `DATABASE_URL=postgres://postgres@localhost/uae_delivery_test node database/test/concurrency.mjs`. With the advisory lock removed from `submit_driver_remittance()` it fails (nine of ten parallel submissions accepted), so it does test the lock.

`transitions.sql` tries every from→to status pair (self-transitions are no-ops and skipped) and compares the database's verdict with a state machine written out independently in the test. `price-consistency.sh` prices 5,000 random bookings with the app's `calculatePrice()` and asks the database's own `shipment_price_is_valid()` to accept each one.

`grade.py` checks every labelled step and exits non-zero if any `ATTACK` got through or any `LEGITIMATE` step errored. Always run it against a fresh database (`run.sh` first) — the battery inserts fixed test users and changes the active pricing rule, so a second run on the same database produces false failures.

Read the output against the `ATTACK:` / `LEGITIMATE:` labels in `attacks.sql` — an `ERROR` after an `ATTACK:` line means it was correctly blocked; an `ERROR` after a `LEGITIMATE:` line means something is actually broken.

`test/0000b_storage_stub.sql` similarly stubs just enough of Supabase Storage's schema (`storage.buckets`/`storage.objects`/`storage.foldername()`) to exercise migration 0012's policies — folder-scoped upload, cross-customer read isolation, and the assigned-driver read path are all covered by `attacks.sql`. It does not replicate Supabase Storage's actual upload API, so a real end-to-end upload still needs a live Supabase project.
